# Evolutionary Design (ED) — Project Architecture Guide

> Самостоятельное практическое руководство по проектированию frontend-приложений по принципам **Evolutionary Design (ED)**.
>
> Документ намеренно не привязан к предметной области, конкретному продукту или репозиторию.
>
> **Источник истины:** публичная документация Evolution Design — https://ed.evocomm.space/guide/
>
> Документ ниже является систематизацией опубликованных принципов ED, а не заменой официальной документации.

---

## 1. Что такое Evolutionary Design

**Evolutionary Design (ED)** — архитектурный подход, в котором проект строится из **абстракций и границ ответственности**, а структура эволюционирует по мере роста системы.

Главная идея ED не в том, чтобы заранее создать максимально сложное дерево каталогов.

Главная идея:

> **Начинай с минимальной структуры и усложняй модуль только тогда, когда текущая форма начинает мешать разработке.**

ED ставит во главу угла:

- смысловую связность;
- слабую связанность между независимыми частями;
- явные архитектурные границы;
- минимальный необходимый уровень абстракции;
- возможность рефакторинга без переписывания всего приложения.

ED сознательно сочетает прагматизм с архитектурными ограничениями. В официальной документации отдельно подчёркивается, что излишняя архитектура хуже её недостатка, а структура должна усложняться только по мере возникновения реальной проблемы. citeturn874963view2

# 2. Для каких проектов предназначен ED

Официальный guide указывает ED как подход для frontend-проектов на основных web-фреймворках, включая:

- React;
- Vue;
- Svelte;
- Solid.

ED не предназначен специально для разработки библиотек, хотя отдельные идеи из него могут быть полезны и там. citeturn262088view0

В официальной документации выделены четыре модификации:

| Модификация | Назначение |
|---|---|
| `ED small` | небольшие проекты; ориентир — до 12 человеко-месяцев и 1–2 frontend-разработчика |
| `ED medium` | средние проекты; ориентир — команда до 5–6 frontend-разработчиков |
| `ED enterprise` | крупные проекты с несколькими командами |
| `ED monorepo` | несколько проектов, развиваемых одной командой |

В текущем публичном guide подробно описаны прежде всего `ED small` и `ED medium`; `enterprise` и `monorepo` обозначены как направления для отдельных будущих материалов. citeturn262088view0turn969890view0

> Важное правило: размеры команд и человеко-месяцы — ориентиры, а не математические ограничения.

# 3. Базовая единица мышления: абстракция

В ED структура проекта рассматривается не просто как набор папок.

Папка, файл, функция, компонент, модуль, группа и слой — всё это способы **создать абстракцию**.

Абстракция позволяет использовать код, не погружаясь каждый раз во все детали его реализации.

Например:

```ts
const user = await createUser(data);
```

Чтобы использовать `createUser`, не требуется каждый раз читать весь код внутри функции.

Тот же принцип применяется к папке-модулю:

```ts
import { Search } from '@/features/search';
```

Потребителю важно знать, **что предоставляет `search`**, а не каким образом внутри расположены UI, state, API и вспомогательные функции.

Официальный deep-dive ED ставит понятие абстракции в основу всей архитектуры: архитектура состоит из создания абстракций, переноса кода между ними и построения связей между ними. citeturn424213search1

---

# 4. Сложность и «кошелёк Миллера»

ED учитывает когнитивную сложность кода.

Человек одновременно способен удерживать ограниченное количество смысловых единиц. Поэтому код, состоящий из большого количества мелких разнотипных частей, может быть сложнее большого файла с одной понятной ответственностью.

Отсюда следует важный ED-принцип:

> **Не дроби код просто потому, что файл стал длинным.**

В официальном guide приведён практический ориентир: файл до примерно 400 строк может оставаться приемлемым на раннем этапе, если такой модуль проще понимать и менять, чем десятки маленьких файлов. citeturn874963view3

Это не норматив на размер файла. Это аргумент против бессмысленного дробления.

# 5. Четыре верхнеуровневых слоя ED

Базовая структура:

```text
src/
├── app/
├── features/
├── services/
└── shared/
```

Это **не просто соглашение о каталогах**.

Это четыре архитектурные границы.

| Слой | Ответственность |
|---|---|
| `app` | запуск приложения, route integration, глобальная конфигурация и композиция приложения |
| `features` | крупные независимые куски функциональности приложения |
| `services` | переиспользуемые бизнес-модули, помогающие features выполнять работу |
| `shared` | ядро приложения и действительно глобальные вещи |

ED отличается от FSD тем, что:

- `features` охватывает крупные функциональные блоки и фактически объединяет смысловые обязанности, которые в FSD разделяются между `pages`, `widgets`, `features`, `entities`;
- отдельного слоя `pages` нет — страницы являются частью feature;
- `services` не ограничены семантикой бизнес-сущности;
- `shared` в ED **может содержать бизнес-логику**;
- вместо терминов FSD «слайс» и «сегмент» в ED используются прежде всего **module** и **group**;
- разрешены вложенные sub-modules. citeturn262088view0

# 6. Направление зависимостей

Базовая модель зависимостей:

```text
app
 ↓
features
 ↓
services
 ↓
shared
```

Но это следует понимать не как жёсткую линейную иерархию импорта для каждого отдельного случая, а как архитектурное направление ответственности.

Ключевые ограничения:

```text
features ──X──> app
services ──X──> app
services ──X──> features
shared   ──X──> app
shared   ──X──> features
shared   ──X──> services
```

При этом:

```text
app       ──> features / services / shared
features  ──> services / shared
services  ──> shared
```

`shared` является самым низким слоем и не должен напрямую зависеть от других верхнеуровневых слоёв. citeturn874963view1turn896018view0

# 7. `app`

## Назначение

`app` — точка входа и место, где приложение собирается в единое целое.

Здесь находится наиболее часто меняющаяся логика интеграционного уровня.

Примеры:

- запуск приложения;
- route initialization;
- root layout;
- global CSS;
- global providers;
- глобальный header;
- интеграция нескольких features в одну страницу;
- Next.js `app` router structure.

Официальный guide подчёркивает, что внутреннее устройство `app` не стандартизировано и зависит от конкретного приложения. citeturn262088view0

---

## 7.1. Что особенно важно в Next.js

В Next.js каталог:

```text
app/
```

остаётся самим собой, потому что он является частью механики Next.js App Router.

ED рекомендует при этом переносить большую часть логики из route-файлов в `features`. citeturn262088view0

Например:

```text
src/
├── app/
│   └── dashboard/
│       └── page.tsx
└── features/
    └── dashboard/
        └── ...
```

`page.tsx` может быть тонким composition entry point.

---

## 7.2. Страница не обязана быть отдельным верхним слоем

В ED нет специального слоя:

```text
pages/
```

Полноценная страница относится к feature, если она является частью одной функциональной области.

Если же одна route-page собирает несколько независимых features, композиция выполняется выше — в `app`. citeturn262088view0

Концептуально:

```text
app/page
    ├── feature A
    ├── feature B
    └── feature C
```

а не:

```text
pages/
widgets/
features/
entities/
```

как обязательные отдельные слои.

---

# 8. `features`

`features` — основной слой ED.

Здесь должна находиться большая часть кода приложения.

Feature — это:

> **крупный независимый кусок функциональности приложения с высокой смысловой связностью.**

Официальный guide специально предупреждает: не следует искусственно делать features мелкими. На раннем этапе нормально иметь всего 3–4 крупные features, а затем естественным образом получать больше. citeturn262088view0

---

## 8.1. Что может находиться внутри feature

Внутри одной feature допустимо иметь:

- UI;
- бизнес-логику;
- model/state;
- API;
- domain logic;
- инфраструктурный код, если он относится к этой функциональности;
- страницу;
- подмодули;
- композиционные элементы.

Не требуется разносить их по глобальным каталогам только ради формального порядка.

Главный критерий:

> Все части должны иметь высокую смысловую связность с feature.

Это одно из ключевых отличий ED от архитектур, где UI, hooks, entities, pages и data logic обязательно разносятся по разным глобальным слоям. citeturn969890search0

---

# 9. Граница между features

Здесь ED различается по модификациям.

## ED small

Прямой импорт одной feature из другой **разрешён**.

Но это не означает, что его следует использовать часто.

Практическое правило:

> Между features должно быть как можно меньше связей; в идеале их не должно быть.

Если одна feature постоянно импортирует другую, это сигнал проверить:

- неверно ли выделены границы features;
- не должны ли они стать одной feature;
- не является ли общий код service;
- не нужна ли dependency inversion. citeturn874963view0

## ED medium

Прямой импорт одной feature из другой запрещён:

```text
features/A ──X──> features/B
```

Это делает features независимыми блоками и уменьшает вероятность циклических зависимостей и каскадных поломок. citeturn424213search2

---

## 9.1. Как features взаимодействуют в medium

Вместо прямых импортов используются слабые формы связи:

- общий state;
- события;
- context;
- slots;
- render props;
- dependency injection;
- передача параметров;
- другие формы dependency inversion.

Это самая сложная архитектурная часть ED, поэтому её не следует насильно вводить в маленьком проекте. citeturn874963view0

---

# 10. `services`

`services` — слой **переиспользуемых бизнес-модулей**.

Это принципиальное уточнение.

Service в ED — не просто:

```text
services/
  email.ts
  logger.ts
  database.ts
```

по принципу «любая общая служебная логика сюда».

Service должен быть самостоятельным модулем, который:

- имеет собственную ответственность;
- не реализует пользовательскую функциональность как feature;
- помогает нескольким features выполнять свою работу;
- может содержать не только логику, но и представление.

Официальный guide прямо описывает `services` как переиспользуемые бизнес-модули и рекомендует выносить код туда только при реальной необходимости. citeturn874963view1

---

## 10.1. Когда нужен service

Плохая причина:

> «Файл большой, вынесем его в services».

Хорошая причина:

> «Эта самостоятельная логика реально используется несколькими features и не принадлежит ни одной из них».

Принцип:

```text
feature A ──> service
feature B ──> service
feature C ──> service
```

---

## 10.2. Services не импортируют features и app

Обязательное ограничение:

```text
services ──X──> features
services ──X──> app
```

Причина — service должен быть более стабильным и переиспользуемым, чем код конкретных features. citeturn874963view1

---

## 10.3. Services могут взаимодействовать друг с другом

В ED базово взаимодействие service-to-service разрешено:

```text
service A ──> service B
```

Автор ED сознательно не навязывает dependency inversion на этом уровне, поскольку это часто усложняет архитектуру сильнее, чем помогает.

Но если связи между services начинают создавать проблемы, можно ввести более строгую изоляцию по аналогии с features. citeturn874963view1

---

## 10.4. Когда не нужен services

В `ED small` этот слой часто вообще не нужен.

Не следует создавать:

```text
services/
```

пустым «на будущее».

Сначала код живёт там, где находится его основная ответственность.

После появления реальной повторяемости создаётся service.

---

# 11. `shared`

`shared` — ядро приложения.

Это самое опасное место с точки зрения архитектурного расползания.

Главное правило:

> **`shared` — последнее место для кода.**

Перед помещением кода сюда нужно задать вопрос:

> Можно ли оставить этот код в feature или service?

Если можно — оставляй выше.

Только когда перенос действительно нецелесообразен, код становится shared. citeturn874963view1

---

## 11.1. Что обычно находится в shared

Официальный guide выделяет прежде всего:

- глобальные бизнес-типы;
- глобальную инфраструктуру;
- глобальные константы, связывающие приложение;
- глобальную конфигурацию;
- глобальные state instances;
- notifications;
- i18n;
- theme;
- UI-kit;
- API infrastructure.

При этом `shared` **может содержать бизнес-логику**, если она действительно глобальная и не принадлежит одной feature. Это принципиальное отличие ED от FSD. citeturn262088view0

---

## 11.2. `shared` не зависит от других слоёв

Нельзя:

```text
shared ──> feature
shared ──> service
shared ──> app
```

Могут:

```text
app       ──> shared
features  ──> shared
services  ──> shared
```

Это одна из самых важных границ всей архитектуры. citeturn896018view0

---

# 12. Стандартные группы внутри `shared`

ED не фиксирует жёсткую структуру `shared`, но предлагает повторяемый набор групп:

```text
shared/
├── domain/
├── model/
├── ui/
├── api/
└── lib/
```

Все они опциональны.

Не нужно создавать их все заранее. citeturn874963view1

---

## 12.1. `shared/domain`

Содержит наиболее важные глобальные бизнес-типы и правила.

Особенно ценны **чистые функции** и типы, не зависящие от UI и инфраструктуры.

Примеры:

```text
shared/domain/
├── ids.ts
├── events.ts
├── user.ts
└── session.ts
```

Если сложная бизнес-логика в `model` превращается в отдельную область чистых вычислений, она может быть выделена в `domain`. Официальный guide приводит как примеры расчёты скидок, прогресса, координат и другие чистые функции с соответствующими типами. citeturn896018view1

---

## 12.2. `shared/model`

Содержит работу с глобальными данными и состоянием приложения.

Примеры:

```text
shared/model/
├── store.ts
├── config.ts
└── routes.ts
```

Здесь может находиться:

- глобальный store instance;
- глобальные state definitions;
- routes/config;
- доступ к глобальному состоянию.

---

## 12.3. `shared/ui`

Глобальный UI-kit и компоненты общего назначения.

Примеры:

```text
shared/ui/
├── button.tsx
├── dialog.tsx
├── table/
│   └── ...
└── input.tsx
```

UI-компонент относится сюда, когда он действительно универсален и не выражает ответственность конкретной feature.

---

## 12.4. `shared/lib`

Глобальная инфраструктура и вспомогательный код.

Примеры:

```text
shared/lib/
├── notifications/
├── i18n/
├── react/
└── date.ts
```

Это не «папка для всего, что больше нигде не подошло».

---

## 12.5. `shared/api`

API — особый случай.

Официальный guide отдельно отмечает, что по своей природе UI-kit и API не являются идеальными кандидатами для `shared`, потому что они часто меняются. Но на практике полностью вынести их из `shared` не удалось, поэтому они остаются распространённым исключением. citeturn874963view1

Поэтому:

```text
shared/api/
```

допустим, но должен рассматриваться как **опасная зона высокой связности**, а не как универсальная свалка всех запросов.

Типичный пример:

```text
shared/api/
├── api-instance.ts
└── generated.ts
```

Конкретный feature-specific API по возможности остаётся внутри соответствующего модуля.

# 13. Module, Group и Layer — это разные понятия

Это один из самых важных разделов ED.

## Layer

Верхнеуровневая архитектурная группа:

```text
app
features
services
shared
```

## Group

Набор нескольких модулей, объединённых общим признаком.

Например:

```text
ui/
hooks/
model/
api/
lib/
```

Группа помогает ориентироваться в большом модуле, но **не создаёт скрытую абстракцию сама по себе**.

Для группы public API не нужен. citeturn874963view5

## Module

Самостоятельная абстракция с публичным интерфейсом.

Когда используется module, потребителю не обязательно знать внутреннее устройство.

Например:

```text
features/
└── search/
```

может быть модулем.

## Sub-module

Модуль внутри другого модуля.

Он может быть практически таким же сложным, как отдельная feature.

ED позволяет использовать sub-modules, если это помогает управлять сложностью. citeturn896018view0

# 14. Public API

Как только внутренний модуль перестаёт быть очевидным, появляется проблема:

> Что из его содержимого предназначено для внешнего использования?

ED предлагает формализовать это через **public API**.

Классический вариант:

```text
module/
├── index.ts
├── ui.tsx
├── model.ts
└── api.ts
```

`index.ts` экспортирует только публичные элементы:

```ts
export { Search } from './search';
```

Потребитель импортирует:

```ts
import { Search } from '@/features/search';
```

а не внутренний файл.

Public API нужен именно **модулю**, а не каждой технической папке. Группы сами по себе public API не требуют. citeturn874963view4turn874963view5

---

# 15. Особенность Public API в Next.js

Официальный guide отдельно предупреждает: с Next.js были ситуации, когда `index.ts` с re-export'ами вёл себя не так удобно с точки зрения tree-shaking.

Поэтому в Next.js допустим другой механизм:

- публичные файлы — без `_`;
- приватные implementation files — с `_`.

Например:

```text
features/search/
├── search-page.tsx
├── _use-search.ts
├── _api.ts
└── _normalize-query.ts
```

Это позволяет обозначать private implementation без обязательного единственного `index.ts`. citeturn874963view4

> Это особенно важно учитывать при проектировании ED-модулей в Next.js.

---

# 16. Explicit Dependencies — `deps.ts`

ED содержит экспериментальный паттерн **explicit dependencies**.

Проблема:

```text
module A
  ├── import feature B
  ├── import feature C
  ├── import service D
  └── import shared E
```

По большому количеству файлов становится трудно увидеть, от чего реально зависит модуль.

Решение — отдельный `deps.ts`:

```text
features/todo-list/
├── index.ts
├── deps.ts
├── todo-list-page.tsx
└── ...
```

В `deps.ts` перечисляются внешние зависимости:

```ts
export { useSession } from '@/features/auth';
export { useSettings } from '@/features/settings';
```

А внутри модуля:

```ts
import { useSession, useSettings } from './deps';
```

Особенно полезно это может быть для `features` и `services`, где допускаются cross-imports. В официальной документации паттерн помечен как экспериментальный. citeturn874963view4

---

# 17. Эволюция модуля — сердце ED

Не существует требования сразу создавать:

```text
ui/
model/
lib/
api/
compose/
index.ts
```

ED специально предлагает четыре стадии эволюции модуля.

```text
Stage 1 → Stage 2 → Stage 3 → Stage 4
```

Переход выполняется только при появлении конкретной проблемы. citeturn874963view2

---

# 18. Stage 1 — Single File Module

Самый простой вариант:

```text
features/todo-list/
└── todo-list.tsx
```

Весь код может находиться в одном файле.

Это нормально.

Официальный guide специально подчёркивает, что небольшой модуль из одного файла иногда быстрее понимать и менять, чем искусственно раздробленный модуль из двадцати маленьких файлов. Файл до порядка 400 строк может оставаться приемлемым, если ответственность очевидна. citeturn874963view3

### Переходить дальше стоит, когда

- файл реально становится неудобным;
- детали мешают понимать основную абстракцию;
- появились естественные самостоятельные части.

Не переходить дальше только потому, что:

> «у нас принято иметь отдельную папку для hooks».

---

# 19. Stage 2 — Flat Module

Код разделяется на несколько файлов, но без лишних групп:

```text
features/todo-list/
├── index.ts
├── todo-list-page.tsx
├── use-todo-list.ts
├── api.ts
└── use-intersection-observer.ts
```

Файлы называются по **смыслу**, а не по технической принадлежности.

То есть лучше:

```text
use-todo-list.ts
```

чем:

```text
hooks/use-todo-list.ts
```

если дополнительная папка не даёт полезной архитектурной информации.

Официальный guide указывает, что flat module хорошо работает, пока внутри находится ограниченное число разнотипных файлов; эмпирический ориентир — около шести. citeturn874963view3

---

# 20. Stage 3 — Grouped Module

Если модулей становится много, но они естественно делятся по признаку, создаются группы:

```text
features/todo-list/
├── index.ts
├── api.ts
├── model/
│   ├── todo-item.ts
│   ├── use-create-todo.ts
│   └── use-update-todo.ts
└── ui/
    ├── todo-item.tsx
    ├── create-todo-form.tsx
    └── todo-details-form.tsx
```

Здесь `model` и `ui` — **группы**, а не обязательно отдельные модули.

Главное различие:

> **Группа помогает навигации, модуль создаёт абстракцию.**

Группа не обязана скрывать свои элементы и не требует public API. citeturn874963view5

Для однородной группы допустимо значительно больше элементов, чем для смешанной flat-папки; официальный guide приводит ориентир до примерно 20 элементов, в зависимости от однородности. Это эвристика, а не лимит. citeturn424213search2

---

# 21. Стандартные группы внутри модулей

## `ui`

UI-компоненты и редкие presentation-oriented hooks, не содержащие сложной логики.

```text
ui/
├── todo-card.tsx
├── todo-form.tsx
└── todo-page-layout.tsx
```

## `model`

Работа с данными и состоянием:

```text
model/
├── use-todo-list.ts
├── todo-list-store.ts
└── todo-list-item.ts
```

Сюда относятся hooks, state-manager logic и другое поведение данных. citeturn896018view1

## `lib`

Инфраструктурные helper-модули и удобные обёртки вокруг browser API или библиотек:

```text
lib/
├── date.ts
└── use-mutation-observer.ts
```

## `api`

Работа с API и типами контрактов.

```text
api/
├── get-items.ts
└── types.ts
```

## `domain`

Чистые бизнес-правила и типы, когда бизнес-логика уже достаточно сложна, чтобы выделить её в отдельную группу.

```text
domain/
├── item.ts
├── calculate-discount.ts
└── compute-progress.ts
```

## `view-model`

Дополнительная специализированная группа для сложной логики, связанной с пользовательским вводом, drag-and-drop, анимациями и другими UI-interaction concerns.

```text
view-model/
├── use-dnd.ts
└── use-animation.ts
```

Эта группа не обязательна и появляется только при необходимости. citeturn896018view1

---

# 22. Вложенные группы

Группы могут содержать другие группы:

```text
ui/
├── fields/
│   ├── text-field.tsx
│   ├── select-field.tsx
│   └── date-field.tsx
├── create-form.tsx
└── update-form.tsx
```

Но глубину нужно контролировать.

Если вложенность начинает затруднять навигацию, лучше пересмотреть структуру модуля или использовать sub-modules. citeturn896018view2

---

# 23. Module + Group не исключают друг друга

Иногда модуль удобно разделить на группы:

```text
todo-list/
├── index.ts
├── api.ts
├── ui/
└── model/
```

А иногда лучше создать sub-modules:

```text
todo-list/
├── index.ts
├── ui/
├── todo-list/
│   ├── index.ts
│   ├── todo-list-page.tsx
│   └── use-create-todo.ts
└── todo-details/
    ├── index.ts
    ├── todo-details-page.tsx
    └── use-update-todo.ts
```

Выбор между group и sub-module зависит от того, нужен ли самостоятельный публичный контракт.

- Нужно просто удобно разложить похожие элементы → **group**.
- Нужно создать отдельную абстракцию с границей → **module/sub-module**.

Официальный guide прямо подчёркивает, что группы не отменяют sub-modules. citeturn896018view2

---

# 24. Stage 4 — Module with Compose

Последний уровень используется, когда внутри большого модуля появляются хаотичные зависимости между sub-modules.

Типичная проблема:

```text
ui A → model B → ui C → model A → ...
```

Вместо этого части делают слабосвязанными, а их совместную работу собирают в `compose`.

```text
todo-list/
├── index.ts
├── api.ts
├── compose/
│   ├── todo-list-page.tsx
│   ├── create-todo-form.tsx
│   └── todo-details-page.tsx
├── domain/
├── model/
└── ui/
```

В `compose` разрешается координация элементов.

Для `ui` используются:

- slots;
- render props;
- composition.

Для `model`:

- events;
- dependency injection;
- параметры;
- другие способы слабой связи.

По смыслу это близко к Dependency Inversion Principle. citeturn896018view2

---

# 25. Главное правило Compose

`compose` — не очередная обязательная папка.

Она появляется только тогда, когда прямые связи внутри большого модуля начинают создавать сложность.

Нельзя проектировать каждый новый модуль сразу так:

```text
compose/
model/
ui/
view-model/
api/
lib/
```

Правильная стратегия ED:

```text
single-file
   ↓
flat
   ↓
grouped
   ↓
compose
```

и переходить дальше только при реальной необходимости. citeturn874963view2

# 26. Каноническое дерево ED

Ниже не обязательный шаблон, а **максимальная форма**, к которой модуль может прийти по мере роста.

```text
src/
├── app/
│   ├── layout.tsx
│   ├── providers.tsx
│   ├── page.tsx
│   └── ...routes/
│
├── features/
│   ├── feature-a/
│   │   ├── index.ts
│   │   ├── deps.ts
│   │   ├── api.ts
│   │   ├── compose/
│   │   ├── domain/
│   │   ├── model/
│   │   ├── ui/
│   │   ├── view-model/
│   │   └── lib/
│   │
│   └── feature-b/
│       └── ...
│
├── services/
│   ├── service-a/
│   │   └── ...
│   └── service-b/
│       └── ...
│
└── shared/
    ├── domain/
    ├── model/
    ├── ui/
    ├── api/
    └── lib/
```

**Не создавай это дерево целиком заранее.**

Реальный проект в ED может законно начинаться так:

```text
src/
├── app/
└── features/
    └── main/
        └── main.tsx
```

А затем постепенно эволюционировать.

# 27. Правило именования

ED предпочитает имена, которые сообщают **смысл**, а не технический тип.

Хорошо:

```text
use-search.ts
search-page.tsx
create-user-form.tsx
normalize-query.ts
```

Менее информативно:

```text
hooks/
components/
utils/
helpers/
things/
```

Папка `hooks` может быть полезной как **group**, когда однородных модулей действительно много.

Но создавать её только потому, что файл является React hook, не обязательно.

Это следует из общего ED-подхода к эволюции flat → grouped: сначала смысловые файлы, затем группы, если число однотипных модулей действительно растёт. citeturn874963view3turn874963view5

# 28. Как определить, где должен жить новый код

Перед созданием файла пройди этот алгоритм.

## Шаг 1. Это часть конкретной функциональности?

Да → помести внутрь соответствующей **feature**.

---

## Шаг 2. Это используется несколькими features и является самостоятельным бизнес-модулем?

Да → рассмотри **service**.

---

## Шаг 3. Это действительно глобальная часть приложения?

Только тогда → **shared**.

---

## Шаг 4. Это route/layout/provider/composition?

Да → **app**.

---

## Шаг 5. Это ещё слишком маленький код для отдельной абстракции?

Не создавай отдельный модуль.

Оставь внутри текущего модуля.

---

# 29. Как определить: группа или модуль

Задай два вопроса.

### Вопрос 1

Есть ли самостоятельная абстракция со своим публичным контрактом?

Если да:

```text
module/
```

### Вопрос 2

Это просто несколько файлов одинакового типа, которые удобно собрать вместе?

Если да:

```text
group/
```

Пример:

```text
ui/
```

обычно group.

А:

```text
search/
```

может быть module.

---

# 30. Как понять, что feature выделена неправильно

Архитектурные сигналы:

### Слишком много взаимных импортов

```text
A → B
B → C
C → A
```

Часто это означает, что границы features выбраны неудачно.

### Feature состоит из одного маленького действия

Например десятки features вида:

```text
open-dialog/
close-dialog/
save-button/
load-user/
```

ED рекомендует не дробить features слишком мелко. citeturn262088view0

### Feature требует другую feature почти повсюду

Возможные решения:

- объединить features;
- вынести действительно общий бизнес-модуль в service;
- использовать dependency inversion;
- изменить границу ответственности.

---

# 31. Как понять, что появился настоящий service

Service обычно появляется, когда выполняются сразу несколько условий:

1. Есть самостоятельная ответственность.
2. Она используется более чем одной feature.
3. Она не принадлежит естественным образом какой-либо одной feature.
4. Она не является просто универсальным helper'ом.
5. Её можно рассматривать как отдельный бизнес-модуль.

Если хотя бы половина этих пунктов не выполняется, сначала стоит оставить код в feature.

---

# 32. Как понять, что `shared` превращается в свалку

Проблемные признаки:

```text
shared/
├── user.ts
├── order.ts
├── checkout.ts
├── use-user.ts
├── use-order.ts
├── order-utils.ts
└── random-helper.ts
```

Вопрос всегда один:

> Почему этот код нельзя было оставить ближе к своей ответственности?

`shared` должен содержать действительно глобальное ядро, а не всё, что оказалось нужно двум файлам. Официальный guide прямо называет `shared` последним местом для размещения кода. citeturn874963view1

---

# 33. Что делать с бизнес-логикой

В ED бизнес-логика не обязана автоматически уходить в отдельный глобальный `domain`.

Возможны три нормальные позиции:

### Локальная бизнес-логика feature

```text
features/orders/
└── model/
```

если правило относится только к orders.

### Переиспользуемая бизнес-логика service

```text
services/pricing/
```

если самостоятельная бизнес-область нужна нескольким features.

### Глобальная доменная логика shared

```text
shared/domain/
```

если правило действительно является частью глобального ядра приложения и должно быть доступно широко.

ED специально допускает бизнес-логику в `shared`, в отличие от FSD. citeturn262088view0

---

# 34. Антипаттерн: глобальные технические папки

Не стоит начинать проект с:

```text
src/
├── components/
├── hooks/
├── services/
├── api/
├── stores/
├── utils/
└── types/
```

Это группировка по технической форме файлов, а не по ответственности.

Следствием обычно становятся:

- сложное понимание feature;
- высокий coupling;
- сложная навигация;
- скрытые зависимости;
- перенос одной функции через множество глобальных каталогов.

ED предлагает сначала создавать смысловой модуль, а затем группировать его внутренности только тогда, когда это реально помогает. citeturn874963view2turn874963view3

---

# 35. Антипаттерн: «feature = один экран»

Экран может быть feature, но feature не обязана быть только экраном.

Feature может включать:

```text
page
ui
model
api
domain
lib
```

если все они относятся к одной функциональности.

Поэтому:

```text
feature = крупная функциональность
```

а не:

```text
feature = обязательно один React component
```

---

# 36. Антипаттерн: premature architecture

Плохой старт:

```text
feature-x/
├── api/
├── compose/
├── domain/
├── model/
├── ui/
├── view-model/
├── lib/
├── deps.ts
└── index.ts
```

когда внутри всего два файла.

Правильный ED-подход:

```text
feature-x/
└── feature-x.tsx
```

и только потом усложнять структуру.

ED специально разработан для постепенной эволюции от простого к сложному. citeturn874963view2

---

# 37. ED Small vs ED Medium — практическая разница

| Вопрос | ED small | ED medium |
|---|---|---|
| Cross-import features | Разрешён | Запрещён |
| Services | Часто не нужен | Обязателен |
| Dependency inversion между features | Обычно необязателен | Важен при необходимости связей |
| Архитектурный overhead | Минимальный | Выше |
| Основной фокус | Быстрое развитие | Независимость и устойчивость модулей |

Ключевой принцип:

> **Не используй ограничения medium, если проект находится на уровне small и эти ограничения сами становятся стоимостью.**

Официальный guide прямо указывает, что запрет cross-feature imports — самая сложная часть, поэтому для маленькой модификации его нецелесообразно навязывать. citeturn874963view0

# 38. ED и Next.js: рекомендуемый подход

Для Next.js практично мыслить так:

```text
src/
├── app/               # Next.js routing + composition
│
├── features/          # основная функциональность
│   ├── auth/
│   ├── dashboard/
│   └── settings/
│
├── services/          # reusable business modules
│
└── shared/            # global core
```

Route-файлы в `app` должны быть тонкими там, где это возможно.

Например:

```tsx
import { Dashboard } from '@/features/dashboard';

export default function Page() {
  return <Dashboard />;
}
```

Если route собирает несколько features:

```tsx
import { Header } from '@/features/header';
import { Dashboard } from '@/features/dashboard';
import { Activity } from '@/features/activity';

export default function Page() {
  return (
    <>
      <Header />
      <Dashboard />
      <Activity />
    </>
  );
}
```

Такая композиция соответствует роли `app` как места, где features связываются в единое приложение. citeturn262088view0

# 39. Практический процесс создания нового проекта

## Этап 1. Создай минимальное дерево

```text
src/
├── app/
└── features/
```

Не создавай всё сразу.

---

## Этап 2. Выдели крупные features

Ищи не компоненты и не страницы, а крупные смысловые функциональные области.

Например:

```text
features/
├── auth/
├── workspace/
└── settings/
```

Начни с небольшого количества features.

---

## Этап 3. Внутри каждой feature используй Stage 1

Начни с одного файла, если это разумно.

---

## Этап 4. Переходи в Flat Module

Когда один файл действительно стал мешать:

```text
feature/
├── index.ts
├── feature-page.tsx
└── use-feature.ts
```

---

## Этап 5. Добавляй groups

Если файлов стало много и они естественно разделились:

```text
feature/
├── ui/
├── model/
└── api/
```

---

## Этап 6. Добавляй sub-modules

Если внутри feature появились самостоятельные крупные области.

---

## Этап 7. Добавляй compose

Только если зависимости между sub-modules стали сложными.

---

## Этап 8. Вводи services

Только когда одна и та же самостоятельная бизнес-ответственность действительно нужна нескольким features.

---

## Этап 9. Вводи строгие medium-ограничения

Если проект достиг масштаба, на котором независимость features становится ценнее простоты cross-imports.

---

# 40. Практический процесс рефакторинга существующего проекта

Не нужно пытаться мгновенно преобразовать старый проект в идеальное дерево.

Рабочий алгоритм:

### Шаг 1

Найди реальные функциональные области.

### Шаг 2

Сгруппируй код вокруг этих областей.

### Шаг 3

Удали необязательные глобальные технические каталоги.

### Шаг 4

Оставь внутри feature то, что принадлежит feature.

### Шаг 5

Повторное использование анализируй после этого, а не до.

### Шаг 6

То, что действительно переиспользуется как самостоятельный бизнес-модуль, вынеси в service.

### Шаг 7

Остаток, являющийся глобальной инфраструктурой/ядром, помести в shared.

### Шаг 8

Установи import boundaries и запреты.

### Шаг 9

После стабилизации структуры эволюционируй модули по Stage 1–4.

# 41. Архитектурный аудит ED

Периодически проверяй проект следующими вопросами.

## App

- Содержит ли `app` в основном integration/composition код?
- Не спряталась ли здесь бизнес-логика feature?
- Не импортируют ли `features` или `services` код из `app`?

## Features

- Являются ли features крупными смысловыми блоками?
- Не слишком ли они мелкие?
- Нет ли большого количества cross-imports?
- Не ошибочно ли несколько features на самом деле одна?

## Services

- Каждый service действительно переиспользуется?
- Это самостоятельный бизнес-модуль?
- Не содержит ли service зависимость на feature?
- Не используется ли `services` как обычная папка `utils`?

## Shared

- Почему каждый элемент находится именно в `shared`?
- Может ли он жить внутри feature?
- Не стал ли `shared` свалкой?
- Не появилась ли глобальная бизнес-логика, которая на самом деле локальна?

## Modules

- Есть ли у модуля ясная ответственность?
- Есть ли нужный public API?
- Не создана ли group там, где нужен module?
- Не создан ли module там, где достаточно группы?
- Не используется ли Stage 4 без необходимости?

# 42. Быстрый decision tree

```text
Новый код
   │
   ├─ относится к одной конкретной функциональности?
   │      └─ да → feature
   │
   ├─ самостоятельный reusable business module для нескольких features?
   │      └─ да → service
   │
   ├─ глобальное ядро / инфраструктура / глобальные типы / UI-kit / API foundation?
   │      └─ да → shared
   │
   └─ route / layout / provider / composition?
          └─ да → app
```

После выбора места:

```text
Маленький модуль?
   ↓
single file
   ↓
Стало неудобно?
   ↓
flat
   ↓
Много однородных частей?
   ↓
grouped
   ↓
Появились крупные самостоятельные части?
   ↓
sub-modules
   ↓
Зависимости стали хаотичными?
   ↓
compose
```

# 43. Золотые правила ED

## Правило 1

**Не проектируй архитектуру заранее на максимальный размер.**

---

## Правило 2

**Код сначала принадлежит своей ответственности, а не глобальному техническому типу.**

---

## Правило 3

**Feature должна быть крупной и смыслово связной.**

---

## Правило 4

**Services создаются по необходимости, а не автоматически.**

---

## Правило 5

**Shared — последнее место для кода.**

---

## Правило 6

**Группа и модуль — не одно и то же.**

---

## Правило 7

**Public API нужен модулю, а не каждой технической папке.**

---

## Правило 8

**Усложняй модуль только тогда, когда текущая форма создаёт проблему.**

---

## Правило 9

**В small допускай простоту, в medium защищай независимость модулей.**

---

## Правило 10

**Архитектура существует ради управляемости изменений, а не ради красивого дерева каталогов.**

---

# 44. Минимальный ED checklist перед merge

```text
[ ] Код находится на уровне ответственности, которому принадлежит
[ ] Новая feature действительно является крупной функциональной областью
[ ] Не создан лишний service
[ ] Не засорён shared
[ ] app не содержит локальную feature-логику без необходимости
[ ] Нет запрещённых layer imports
[ ] Для medium нет direct feature → feature imports
[ ] Module имеет понятный public API, когда он уже нужен
[ ] Group не используется как фиктивный module
[ ] Структура не усложнена раньше времени
[ ] Текущий уровень эволюции модуля оправдан реальной проблемой
```

# 45. Краткая эталонная модель

ED удобно держать в голове так:

```text
                    APPLICATION
                         │
                        app
                         │
             ┌───────────┴───────────┐
             │                       │
         features                features
             │                       │
             └──────────┬────────────┘
                        │
                     services
                        │
                      shared
```

А внутри каждого сложного модуля:

```text
module
├── public API
├── groups
├── sub-modules
└── compose
```

Но эти элементы **не обязаны существовать одновременно**.

Эволюционная последовательность:

```text
simple → flat → grouped → sub-modules → compose
```

# 46. Важная философия ED

ED — не набор обязательных папок.

Это способ управлять сложностью через постепенно возникающие абстракции.

Нельзя сказать:

> «Правильный ED-проект обязан иметь именно такое дерево».

Правильнее сказать:

> **Правильный ED-проект имеет понятные границы, минимально необходимое количество абстракций и структуру, которая естественно эволюционировала из реальных потребностей системы.**

Именно поэтому самый «архитектурный» проект иногда имеет очень простое дерево, а большой модуль — много групп, sub-modules и `compose`.

Официальная документация подчёркивает тот же баланс: ED одновременно стандартизирует понятия и сохраняет гибкость и прагматизм. citeturn896018view2
